これから実装するタスクのテスト計画を作成してください。引数: $ARGUMENTS(タスクの説明。省略時は会話の文脈・PR本文・参照されたチケットから把握する)

テスト計画は「このタスクが正しく終わったと言える条件」を **テストとして実行できる形** で並べたものです。/test-check が実装後にこの計画と実際のテストを突合します。

## 手順

1. タスクの内容を把握する。優先順位: $ARGUMENTS → 会話の文脈 → `gh pr view --json title,body`(ドラフト PR があれば) → 参照されたチケット・Slack・Notion の依頼文 → 関連する既存仕様(docs/, README, CLAUDE.md)
2. リポジトリのテスト環境を確認する: テストフレームワーク(pytest / jest / vitest / playwright 等)、テストの置き場所、実行コマンド(package.json / Makefile / CLAUDE.md から)。**分からなければ推測せず「要確認」に書く**
3. 不明点が実装の成否に関わる場合だけ、計画を書く前にユーザーに質問する(最大3問。細部は「要確認」として計画に残してよい)
4. 現在のブランチ名を取得し、`.claude/specs/<ブランチ名のスラッシュを-に置換>.md` に以下の形式で書く:

```markdown
# テスト計画: <タスク名>
作成: <日付> / ブランチ: <ブランチ名>
テスト実行: `<コマンド>` / 置き場所: <パス>

## 目的(1〜2行)

## テストケース
各ケースは「前提 / 操作 / 期待結果」で、外から観測できる振る舞いを書く。
- [ ] TC-1 <正常系: 〜のとき〜になる>
- [ ] TC-2 ...
- [ ] TC-3 <エッジ: 空・0件・境界値・重複・同時実行・途中失敗>
- [ ] TC-4 <既存動作の維持: 〜は変わらない>

## 変更してはいけないこと(非目標)
- NG-1: ...

## 要確認(仕様が曖昧な点)
- Q-1: ...
```

5. 書いた計画をユーザーに提示し、**承認を得る**
6. 承認後、テスト環境が判明していれば、TC ごとに **失敗する(または skip 状態の)テストの雛形** を作ることを提案する。テスト名またはコメントに `TC-n` を含める(/test-check が機械的に対応づけられるように)。作るかどうかはユーザーの判断に従う
7. `${CLAUDE_PLUGIN_ROOT}/scripts/events-log.sh test_plan.created cases=<TC数>` でログに記録する(スクリプトが無ければ `find ~/.claude/plugins -path '*test-plan*' -name events-log.sh | head -1`)

## ルール

- テストケースは「コードがどう書かれるか」ではなく「外から観測できる振る舞い」で書く
- 1タスクのケースは 5〜12 個程度。それを超えるならタスク分割を提案する
- 実装中に仕様が変わったら、コードではなく **先にこのファイルを更新** する
- 既存のテストで既にカバーされている振る舞いは、そのテスト名を添えて「既存」と書く(新しく書かない)
