---
description: 実装後に、テスト計画の各ケースに対応するテストが存在し・実行され・通っているかを確認し、計画外の振る舞い変更が混ざっていないかを見る
allowed-tools: Bash, Read, Grep, Glob, Task
---

実装が終わった変更に対して、テスト計画との突合を行ってください。引数: $ARGUMENTS(比較元ブランチ。省略時は自動判定)

あなたの役割は「仕様を満たしていないコードが PR に出るのを防ぐ」ことです。品質(セキュリティ・性能・設計)は見ない(review-loop の担当)。

## 手順

1. スクリプトの場所を特定する: `${CLAUDE_PLUGIN_ROOT}/scripts/`。無ければ `find ~/.claude/plugins -path '*test-plan*' -name review-diff.sh 2>/dev/null | head -1` の dirname
2. 差分を取得する: `<scripts-dir>/review-diff.sh --stat $ARGUMENTS` で比較元と変更ファイル一覧を取得してユーザーに提示し、`<scripts-dir>/review-diff.sh $ARGUMENTS` で全文差分を取る
3. テスト計画を読む: `.claude/specs/<現在のブランチ名のスラッシュを-に置換>.md`
   - **無い場合**: 差分から「この変更が満たそうとしている振る舞い」を TC 形式で 3〜8 個に逆算して書き起こし、ユーザーに「合っているか」を確認する(30秒で答えられる粒度)。承認された内容を上記パスに保存してから続行する(逆算した旨をファイル先頭に明記)
4. **突合**: 各 TC について次を確認する
   - 対応するテストが存在するか(テスト名・コメント内の `TC-n`、無ければ内容から判断。Grep で実際に探す)
   - そのテストを **実際に実行** して通るか。個別確認は計画の実行コマンドで対象を絞ってよいが、最後に必ず `<scripts-dir>/run-tests.sh` で全体を 1 回実行する(結果が .git/ に記録され、/build の完了判定に使われる)
   - 「既存」と書かれたケースは既存テストが通ることを確認する
5. **計画外の変更の検出**: 差分のうち、どの TC・NG にも対応しない振る舞いの変更(関数の戻り値・API レスポンス・DB スキーマ・画面表示の変更)を洗い出す。変更された関数の呼び出し元を Grep で確認し、破壊的変更がないか見る
6. 結果を以下のフォーマットで報告する:

```
# テスト確認結果(比較元: <base> / 計画: <パス>)

| TC | 内容 | テスト | 実行結果 |
|----|------|--------|----------|
| TC-1 | ... | tests/foo_test.py::test_tc1 | ✅ pass |
| TC-2 | ... | (未作成) | ❌ なし |

## 計画外の振る舞い変更
- ファイル:行 — 何が変わったか / 影響する呼び出し元 / 意図したものか要確認

## 判定: 合格 / 不合格(理由)
```

7. ログに記録する: `<scripts-dir>/events-log.sh test_check.result planned=<TC数> covered=<テストがあり通った数> unplanned=<計画外の変更数> verdict=<pass|fail>`
8. **合格**(全 TC にテストがあり通っている、かつ計画外の変更が無いか、あってもユーザーが意図したと確認した)なら `<scripts-dir>/mark-tests-passed.sh $ARGUMENTS` を実行してマーカーを書く。不合格ならマーカーは書かず、足りないテスト・落ちているテストを列挙して終了する

## ルール

- テストを弱めたり skip にして「通った」ことにしない。落ちているテストは落ちていると報告する
- テストが無い TC を「実装を読んで大丈夫そう」で合格にしない。無いものは無い
- 仕様が曖昧で合否を判定できない項目は、推測せず「要確認」として質問形式で出す
- 修正はしない。不足しているテストの作成や実装の修正はユーザーの指示で行う
